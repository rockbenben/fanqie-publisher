# 缺章补发工具（republish）

把定时发布中段漏掉的章节，按番茄原排期节奏补回平台。

> **两个入口，同一套核心**：GUI 主界面有「补漏章」按钮（推荐日常用），
> 本 CLI 供批处理/排查。二者共用 `fanqie_upload.compute_gap_schedule` 的
> 缺口排期计算，行为一致。

## 为什么会漏章

定时发布曾有"确认发布按钮消失=成功"的**假成功 bug**：对话框被异常关闭
（Escape 残留 / 点击被吞后 DOM 重建 / 弹窗抢焦点）时按钮同样消失，章节其实
没提交，却被记成功。番茄填正文时会自动存草稿，于是每个假成功 = 平台上一个
**时间线缺口** + 草稿箱一份**孤儿草稿**。一本书 748 章定时发布实测漏掉 151 章
（日志全记成功、平台却无此章）。

根因已在 `fanqie_upload.py` 修复（`_await_submit_confirmation`：按钮消失后须
「接口 code=0」或「导航到 chapter-manage」二次确认，否则判失败重试）。本工具
负责把**已经漏掉的**章节补回去。

## 设计（防重复、可分月安全重跑）

1. **每次运行先抓平台真实章节列表**，只补"平台上确实还没有"的章。已补的
   自动跳过——重跑绝不产生重复章。
2. 缺口的补发时间按番茄原排期的 **9 槽位网格**（07:00/:01/:02、12:00/:01/:02、
   20:00/:01/:02）在前后邻章之间填空算出，保证插到正确阅读位置、时间单调。
   槽位数与缺章数不符时退化为"邻章间均匀插值"并**告警**（真实数据 0 次触发）。
3. 撞每月/每日字数上限**自动中止并如实记账**；下月重跑会重新抓平台、从断点
   继续（跳过本月已补的）。

## 用法

```bash
# 只看当前缺哪些 + 补发时间，不发布（随时可跑，只读）
python tools/republish/republish.py --dry-run

# 灰度：先补一章，人工核对它是否插到正确位置、时间/状态对
python tools/republish/republish.py --only 709

# 指定章号区间
python tools/republish/republish.py --range 709-1073

# 本次最多补 N 章（分月控量，避免一次撞每月上限）
python tools/republish/republish.py --limit 300 --all

# 补全部当前缺口
python tools/republish/republish.py --all
```

`book_id` 默认取 `.gui_state.json` 的 `last_book_id`，章节目录默认取
`config.json` 的 `chapters_dir`，可用 `--book-id` / `--content-dir` 覆盖。

## 推荐流程

1. `--dry-run` 看缺口清单和排期，确认无告警、本地文件齐全。
2. 有额度时先 `--only <首个缺章>` 灰度一章，到番茄后台核对它是否按章节号
   插到正确阅读位置、时间正确、状态=待发布。
3. 确认无误后 `--all`（或用 `--limit` 分月）。撞每月上限会自动中止，下月直接
   再跑 `--all`，工具会跳过已补的、从断点继续。
4. 全部补完后，草稿箱里那批孤儿草稿可批量清理。

## 每月字数上限

补 151 章约 40 万字。若账号月额度一次装不下，跑到撞"每月上限"会自动中止。
下月额度重置后再跑 `--all` 即可续补，无需手动记进度（工具按平台真实状态判定）。

## GUI 入口

主界面主行动条上的「**补漏章**」按钮做同样的事：先刷新平台章节（切到「修改
内容/修改排期」或它会提示加载），再点「补漏章」→ 弹出"本次最多补 N 章"→
预览确认 → 在日志面板带进度补发。撞上限自动中止，再点即续补。

## 文件

- `republish.py` —— CLI 工具（抓平台 + 算缺口排期 + 补发，自包含）。
- `republish_plan.json` —— 排期快照（2026-07-25 基线，仅章号/日期/时间，
  作记录用；每次 `--dry-run`/运行会按平台真实状态刷新，不含本地绝对路径）。
- 缺口排期核心在 `fanqie_upload.compute_gap_schedule`（CLI 与 GUI 共用），
  逻辑由 `tests/test_republish_schedule.py` 锁定（零依赖）。
